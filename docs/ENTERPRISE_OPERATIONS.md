# RuleLab 0.6: controlled workspace operations

This release implements an enterprise-style workspace and bounded specialist-agent orchestration. It is ready for a controlled, single-workspace pilot after credentials and deployment settings are configured. It is not a certified production SaaS or a multi-tenant platform.

## Implemented controls

| Control | Behavior |
|---|---|
| Named access keys | Each configured bearer credential has an actor ID and an admin/editor/reviewer/viewer role. No credential is sent to the UI by the server. |
| Authorization | Viewer reads/exports; reviewer also records human review; editor edits and executes analysis/jobs; admin also has operational control. All authorization is enforced server-side. |
| Production startup | Requires named keys, at least one admin and an explicit HTTPS origin allowlist. Invalid capacity/timeout configuration fails startup. |
| Audit | Auth failures, denials and API mutations record actor, role, request ID, endpoint, response status and timestamp. Document bodies and bearer credentials are excluded. SQLite logs are not tamper-proof. |
| Request protection | Declared and actual mutation body sizes are capped at 15 MB. Requests carry an X-Request-ID; API responses use no-store. Origin checks, CSP and content-type protections remain enabled. |
| Agent jobs | Persisted snapshots, plan, tool events, results, failures, timeouts and cancellation. At most one active job per draft and a configurable global job limit. |
| Idempotency | Job submission requires Idempotency-Key. Reusing a key with the same payload returns the original job; a different payload returns conflict. |
| Safe revisions | Jobs never edit drafts. Existing optimistic revision checks and explicit human review/application remain in force. |
| Recovery | Unexpected restart marks unfinished jobs interrupted; it never silently reruns potentially billed provider calls. Completed partial results remain accessible. |
| Backup | scripts/backup_workspace.py uses SQLite online backup, an integrity check and restrictive file permissions. |

## What the agents actually do

A coordinator plans a requested legal/impact/full workflow. In Gemini/Vertex mode, its rationale is generated by the model and validated against an allowed workflow schema. In demo mode it is explicitly deterministic. The planner cannot expand the requested scope, invoke shell commands, browse arbitrary URLs, change laws or publish documents.

The research role executes the existing source-retrieval tool. The legal-review role invokes the existing source-bound analysis and quote/rule validators. The impact role runs the quantitative assumption model and synthetic stakeholder perspectives. A final quality event records the validators applied and human-review requirement. Tool starts, completions and failures are real backend events. The UI summarizes the latest state per tool and exposes the complete event ledger separately. This is a bounded graph of specialist roles, not an open-ended autonomous research system or a calibrated population simulator.

Job outputs are normal analysis/simulation runs and can be opened, reviewed and exported using existing workflows. The model is not allowed to automatically apply them. Changing a draft does not change a running job's snapshot.

## Local pilot

Run ./start.sh. Development mode without configured keys is intentionally local-admin mode. Keep it bound to 127.0.0.1. Enable Gemini or Vertex using existing .env instructions and verify with scripts/verify_live.py. Provider planning/review/perception quality has not been validated live in this build.

To use named credentials, generate a distinct random token for each actor on your own host:

```bash
python3 -c 'import secrets; print(secrets.token_urlsafe(48))'
```

Set RULELAB_ACCESS_KEYS as a JSON array with exactly id, role and token for each credential. Each token must have at least 32 characters; actor IDs and tokens must be unique. Example shape, with placeholders that must be replaced:

```dotenv
RULELAB_DEPLOYMENT_MODE=production
RULELAB_ALLOWED_ORIGINS=https://rulelab.your-company.example
RULELAB_ACCESS_KEYS='[{"id":"team-admin","role":"admin","token":"REPLACE_WITH_A_RANDOM_ADMIN_TOKEN"},{"id":"legal-editor","role":"editor","token":"REPLACE_WITH_A_RANDOM_EDITOR_TOKEN"},{"id":"legal-reviewer","role":"reviewer","token":"REPLACE_WITH_A_RANDOM_REVIEWER_TOKEN"},{"id":"legal-viewer","role":"viewer","token":"REPLACE_WITH_A_RANDOM_VIEWER_TOKEN"}]'
RULELAB_MAX_AGENT_JOBS=4
RULELAB_AGENT_STEP_TIMEOUT=180
```

The browser asks for a server token when API authentication is enabled and keeps it in sessionStorage. This is named bearer access, not SSO or an account-management service. Rotate credentials via the secret configuration and restart. All actors share one workspace.

## Deployment and persistence

Use exactly one Uvicorn worker and one application instance, with durable local SQLite storage. The worker owns cancellation and capacity accounting. Do not run multiple replicas or multiple workers against this implementation. Docker already runs as a non-root user; mount a durable volume at /app/var. Terminate TLS at a configured reverse proxy and supply the HTTPS origin allowlist. Use gateway rate limits for expensive direct AI endpoints and searching. Production-mode startup validates configuration, not the reverse proxy, secret strength or organizational compliance.

Do not run the SQLite job store on ephemeral Cloud Run storage. Multi-instance deployments require moving canonical data/jobs/audit to a shared transactional database and deploying a durable queue/worker service before scaling.

Create a backup on the application host using the configured environment:

```bash
python3 scripts/backup_workspace.py /secure-backups/rulelab-2026-10-11.sqlite3
```

Restore only with the application stopped. Keep backups encrypted and access-controlled. Back up source/configuration files separately, then rehearse restore and validate revisions, runs, jobs and audit on a staging copy. The included test verifies database backup integrity and retained records, not an operational RPO/RTO guarantee.

## Remaining production integrations

- Organization SSO/OIDC, managed user lifecycle, MFA and tenant isolation.
- Shared database/queue, high availability and deployment/load/penetration tests.
- Secret-manager integration, encrypted storage, alerting, retention and audited backup/restore policy.
- Actual Gemini/Vertex IAM, quotas, response quality and cost tests; real Elasticsearch retrieval evaluation.
- Expert legal acceptance, amendment/court coverage and current-law consolidation.

These are explicit limits, not enabled features. The UI never claims an SSO connection, compliance certification, empirical impact accuracy or verified current-law status.
